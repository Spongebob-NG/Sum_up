# Linux 网络底层收包机制与数据流向核心笔记

## 一、 核心实体与数据结构分工

Linux 网络栈采用“软硬分离、分层抽象”的设计架构，各核心实体的边界与职责划分如下：



| **实体名称**                   | **归属层级**        | **存储形态与物理属性**                                       | **核心职责**                                                 |
| ------------------------------ | ------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **Ring Buffer (硬件收发队列)** | 网卡硬件 / 驱动层   | **连续物理内存中的结构体实体数组**（非指针数组，通常 16/32 字节对齐） | 存放 DMA 描述符（DMA Descriptor）。供网卡控制器读写物理内存地址、包长度及硬件完成标志位（DD/EOP）。 |
| **DMA 缓冲区**                 | 物理主机内存        | 由驱动预先分配的一整块连续物理内存                           | 真实存放以太网原始二进制报文（Payload）的介质。              |
| **`struct sk_buff`**           | 内核网络协议栈      | 内核堆内存中的大型软件管理结构体（200+ 字节）                | 内核网络包的“大管家”。通过 `head/data/tail/end` 四个指针管理报文生命周期与分层解包偏移。 |
| **`struct socket`**            | VFS 虚拟文件系统    | 对应用户态 `sockfd` 的文件系统层抽象                         | 面向应用层系统调用（`read/write/epoll`），持有指向底层 `struct sock` 的指针。 |
| **`struct sock`**              | 传输层/网络层协议栈 | 具体协议连接的核心控制块（如 TCP 对应 `struct tcp_sock`）    | 管理协议状态机、滑动窗口、拥塞控制算法，维护连接专属的接收队列 `sk_receive_queue`。 |

## 二、 全链路收包时序与数据流向

从物理网线接收信号到用户态 C++ 变量拿到底层数据的完整流转如下：



```
[网线电/光信号]
       │
       ▼
1. 网卡 DMA 写入物理内存 (skb->data 指向的裸缓冲区)
       │
2. 网卡硬件回写描述符 (设置 length, 标志位 DD/EOP 置 1)
       │
3. 触发 CPU 硬件中断 (Hard IRQ)
       │
       ├─► CPU 关闭网卡硬件中断掩码 (屏蔽后续硬中断)
       ├─► 调度软中断轮询 (napi_schedule)
       └─► 硬件中断迅速退出 (< 1 微秒)
       │
4. 内核软中断运行 (NET_RX_SOFTIRQ / ksoftirqd 轮询 Ring Buffer)
       │
       ├─► 取出对应 sk_buff，重填新的空缓冲区到 Ring Buffer 槽位
       ├─► 驱动层: skb_pull(14) 跳过以太网头
       ├─► 网络层: ip_rcv 校验并跳过 IP 头，运行 Netfilter 防火墙
       ├─► 传输层: tcp_v4_rcv 提取四元组
       │            └─► 在全局哈希表 (inet_hashinfo) 中 O(1) 锁定目标 struct sock
       │
5. 挂入接收队列: 调用 skb_queue_tail() 将 skb 挂入 sock->sk_receive_queue 双向链表
       │
6. 唤醒机制: 触发 sock->sk_data_ready()，将休眠的 epoll_wait 或 recv 线程唤醒
       │
7. 用户态读取: C++ 调用 recv(fd, buf, ...) 陷入内核
       │
       ├─► 从 sk_receive_queue 链表头取出 sk_buff
       ├─► copy_to_user() 将纯业务 Payload 拷贝至用户态 buf
       └─► 释放 sk_buff 内存，系统调用返回
```

## 三、 中断模型与 NAPI 状态机机制

为了防止高速网络下网卡频繁打断 CPU 引发“活锁（Live Lock）”，Linux 采用 **NAPI（中断 + 轮询）混合机制**：



```
[硬中断到来] ──► 关闭网卡中断掩码 ──► 触发软中断 ──► 硬中断返回
                                        │
┌───────────────────────────────────────┴───────────────────────────────────────┐
│ 软中断循环轮询 (每次配额 Budget = 64 个包)                                   │
│                                                                               │
│ ├──【分支 A：收割完 64 个包后，Ring Buffer 依然有新包】                       │
│ │    └── 保持关闭硬中断，主动让出微量 CPU 时间片后进入下一轮软中断轮询。     │
│ │                                                                             │
│ └──【分支 B：当前批次收割完毕，Ring Buffer 已彻底清空】                       │
│      └── 软中断退出轮询，写网卡寄存器【重新开启硬件中断使能】。               │
└───────────────────────────────────────────────────────────────────────────────┘
```

- **硬中断职责**：仅负责“按门铃”，通告有数据到达，随后立即被屏蔽，执行时间极短。
- **软中断职责**：负责“干重活”，执行包括描述符回收、内存重填、GRO 合包、各层协议解析、四元组查找、队列挂载与线程唤醒。
- **硬中断恢复时机**：**仅在 Ring Buffer 内部积压的包被彻底清空时才恢复**，避免高并发下陷入 `中断 -> 轮询 -> 立即中断` 的无效上下文切换循环。

## 四、 核心认知纠偏与机制细节

1. **Ring Buffer 不存指针**：
   - 若存指针，网卡 DMA 控制器访问每个描述符都需要经过 PCIe 两次寻址（先读指针，再读实体），导致总线延迟翻倍。
   - 真实方案是使用 `dma_alloc_coherent()` 申请物理连续内存，将固定大小（如 16 字节）的描述符平铺展开。
2. **协议解包发生在入队之前，而非用户态读取时**：
   - 数据包到达网卡时没有任何 Socket 归属信息。
   - 必须先在内核软中断中解开以太网头、IP 头、TCP 头，提取“源 IP、源端口、目的 IP、目的端口”四元组，在全局哈希表中查出具体的 `struct sock`，才能确定挂入哪个 Socket 的接收队列。
3. **“剥洋葱”零拷贝特性**：
   - 协议解析过程不搬移真实数据内存，只通过操作 `sk_buff` 内部指针（如 `skb_pull` 递增 `data` 指针跳过报头）来实现分层剥离。
4. **全链路唯一的数据拷贝**：
   - 传统协议栈中，唯一一次真正发生的大块内存数据搬移发生在应用层调用 `read()`/`recv()` 时，由内核调用 `copy_to_user()` 将数据从内核空间拷贝至用户空间变量。

## 五、 工程实战与性能排障映射（机器人 / 嵌入式 / 智驾）

在激光雷达高频点云传输、相机网络传输或 ROS2 高吞吐通信场景下的调试排障依据：

```
                 [硬件/驱动层丢包]
                 ethtool -S <interface> | grep rx_dropped
                 成因: Ring Buffer 满、软中断轮询不及时、CPU %si 飙高至 100%
                 解决: 增大 Ring Buffer 深度 (ethtool -G)、调整 CPU 中断亲和性

                                       │
                                       ▼

                 [传输层/系统调用层丢包]
                 抓包显示 TCP ZeroWindow 或 netstat -s 观察 buffer overflow
                 成因: 协议栈正常解包，但 C++ 业务线程卡死/耗时过长，未及时调用 recv()
                 解决: 优化用户态消费线程、加大 SO_RCVBUF、将网络 IO 迁移至独立线程

                                       │
                                       ▼

                 [极致性能与极低延迟场景 (Kernel Bypass)]
                 传统链路瓶颈: sk_buff 分配与回收开销、软中断跨核切换、copy_to_user 内存拷贝
                 工业界解决方案: 采用 AF_XDP (XDP) 或 DPDK，使用 UMEM 共享内存绕过内核协议栈，
                                实现用户态直接读写硬件描述符的零拷贝链路。
```
